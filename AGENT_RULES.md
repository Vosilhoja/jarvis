Правила для агентов Jarvis
=========================

Цель: установить единый свод правил, которых должен придерживаться любой автоматический агент (локальный или удалённый), взаимодействующий с кодовой базой и системой пользователя.

Общие принципы
- Безопасность прежде всего: никогда не выполнять опасные или деструктивные операции без явного многоэтапного подтверждения от пользователя.
- Минимизация побочных эффектов: по умолчанию — dry-run / эмуляция всех операций, которые меняют состояние системы. Настоящее выполнение — только по явному, однозначному согласию пользователя.
- Приватность: команды управления локальным компьютером и привязанные к нему данные должны обрабатываться локально (локальная LLM / правило-рутер), а для знаний/вики можно обращаться к облачным сервисам (Gemini) только по необходимости.
- Ясность и отслеживаемость: каждый автоматический шаг логируется со ссылкой на исходную инструкцию и используемый prompt/правило.
- Использовать стандартные, проверенные библиотеки вместо хаков: если функциональность доступна в надёжной библиотеке (pyautogui, psutil, pyperclip, mss, pillow, pycaw и т.д.), использовать её — не изобретать велосипед.

Правила поведения агента
1. Аутентификация и авторизация
   - Агент должен подтверждать, что запрос пришёл от доверенного источника (например, проверка токенов, Telegram chat_id в whitelist и т.д.).

2. Подтверждения для опасных операций
   - Всякая операция, содержащая намерения: shutdown, restart, format, delete (удаление файлов или очищение корзины), factory reset, erase, или изменение файлов конфигурации на уровне системы — должна требовать явного подтверждения пользователя через inline-клавиатуру или многошаговый flow.
   - Подтверждение не может быть опциональным и должно сохраняться в логах.

3. Dry-run по умолчанию
   - Перед выполнением любой системной команды агент должен сначала выполнить dry-run (эмуляция) и показать пользователю ожидаемые эффекты.
   - Только после явного подтверждения — агент может переключиться в реальный режим и выполнить действие.

4. Авто-тестирование новых функций
   - При добавлении новой функции в кодовую базу агент должен автоматически регистрировать её в реестре тестов (.auto_test_registry.json).
   - Для авто-регистрации функция должна иметь docstring с меткой AUTO_TEST: указывающей пример аргументов (JSON-подобно) или пустые скобки [] — например:
     """AUTO_TEST: ["пример", 123]
     """
   - Если docstring содержит ключевые слова опасных операций, функция помечается как "skipped" в реестре и не выполняется автоматически.

5. Логирование и отчётность
   - Агент обязан записывать логи всех действий в jarvis.log с указанием: кто (agent id), что сделал, какие данные были использованы (prompt, args — без секретов), timestamp, результат.
   - Результаты автоматических тестов сохраняются в .function_test_report.json и .auto_test_registry.json.

6. Использование внешних и локальных LLM
   - Для вопросов про факты, Википедию и общие знания использовать облачные модели (Gemini) через отдельный шлюз.
   - Для управления локальным ПК и действий с повышенными привилегиями использовать локальную LLM (ollama) или rule-based локальный парсер.
   - Ответственность за обработку пользовательских данных: не отправлять в облако чувствительные локальные данные без явного разрешения.

7. Библиотеки и надёжность
   - Использовать топовые, поддерживаемые библиотеки вместо самодельных хаков: предпочтение стандартным и well-known пакетам.
   - Если код вынужден использовать platform-specific hack (например, ctypes для WinAPI), снабдить это подробной документацией и fallback'ами.

8. Тестирование и CI
   - Все автоматически сгенерированные тестовые сценарии должны проходить dry-run локально при добавлении новых функций.
   - CI должен запускать тестер функций в эмуляционном режиме и фейлить при обнаружении regression в side-effect-операциях.

9. Прозрачность проактивности
   - Агент может предлагать напоминания/проактивные действия только если пользователь включил проактивность. По умолчанию проактивность выключена.

10. Обновление и расширение правил
   - Правила хранятся в AGENT_RULES.md в корне репозитория. Любые изменения в правилах должны быть помечены коммитом и обсуждены ревью.

---

Примеры практик для разработчиков
- Добавляя новую функцию, снабжайте её docstring меткой AUTO_TEST с примером аргументов.
- Помечайте функции, которые потенциально опасны, явно меткой в docstring: "DANGEROUS: reason".
- Используйте стандартные библиотеки (pyautogui, psutil, pyperclip, pillow, mss, requests) и документируйте необходимость прямого WinAPI только когда библиотека не обеспечивает нужной функциональности.
